# Jetpack Compose Bytecode Instrumentation

Exploring how to inject UI into a Jetpack Compose function using ASM.

## How it works

The application contains a Composable like this:

```kotlin
@Composable
@InjectComposable
fun MainComposable() {
}
```

There is no call to the UI I want to inject, that UI lives in a small separate module:

```kotlin
@Composable
fun InjectedBadge() {
    Text("Injected by ASM")
}
```

Conceptually, we're turning this:

```kotlin
@Composable
fun MainComposable() {
}
```

into this:

```kotlin
@Composable
fun MainComposable() {
    InjectedBadge()
}
```

without changing the application's Kotlin source.

## But `InjectedBadge()` doesn't exist like that in bytecode

By the time ASM sees our classes, Kotlin and the Compose compiler have already compiled them.

So this:

```kotlin
@Composable
fun InjectedBadge()
```

has become a JVM method that looks roughly like:

```text
InjectedBadge(
    Composer,
    int
)
```

For this experiment, its descriptor is:

```text
(Landroidx/compose/runtime/Composer;I)V
```

The same thing happens to `MainComposable()`, its generated method already receives the current `Composer`.

We can reuse it.

## Finding the `Composer`

Instead of assuming that the `Composer` is always in a specific local variable, we can inspect the method descriptor:

```kotlin
val argumentTypes = Type.getArgumentTypes(descriptor)

val composerArgument = argumentTypes.indexOfFirst {
    it.descriptor == "Landroidx/compose/runtime/Composer;"
}
```

Then calculate its local-variable slot.

For our simple top-level Composable, the generated arguments are effectively:

```text
slot 0 → Composer
slot 1 → changed mask
```

So when we want to call `InjectedBadge`, we already have the `Composer` we need.

## Where should we inject the call?

My first instinct was to insert the call at the beginning of the method or before `RETURN`.

But Compose-generated functions have their own execution and skipping logic.

The generated bytecode contains a call similar to:

```text
Composer.shouldExecute(...)
IFEQ skipLabel
```

`IFEQ` jumps to the skip path when Compose decides that the body doesn't need to execute.

So I insert my call immediately **after** that jump instruction.

That means the injected Composable runs only on the normal execution path of the host Composable.

Conceptually:

```text
shouldExecute(...)
IFEQ skip

InjectedBadge()   ← injected here

original body...

skip:
```

## The actual bytecode is tiny

Once we have the injection point and the `Composer`, the actual insertion is only three instructions:

```kotlin
visitVarInsn(
    Opcodes.ALOAD,
    composerLocal,
)

visitInsn(
    Opcodes.ICONST_0,
)

visitMethodInsn(
    Opcodes.INVOKESTATIC,
    "com/composechef/instrumentation/runtime/InjectedUiKt",
    "InjectedBadge",
    "(Landroidx/compose/runtime/Composer;I)V",
    false,
)
```

That's really the whole injection.

We load the current `Composer`, push the changed-mask value expected by this no-argument Composable, and call the compiler-generated static method.

## Why not generate the whole Composable with ASM?

Technically, I could go much further and try to generate the actual Compose UI instructions myself.

But then I would also be taking responsibility for implementation details normally handled by the Compose compiler: composition groups, skipping, recomposition information, tracing, and more. (That's too much headache !!!)

## Project structure

- `app` contains the sample application and the bytecode instrumentation logic.
- `instrumentation-runtime` contains the `@InjectComposable` annotation and the UI that is injected.

The visitor is declared directly in `app/build.gradle.kts`, but in a real-world scenario, it could be placed in a reusable binary plugin.
